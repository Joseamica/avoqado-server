### No imprescindible para el primer pedido v1
- Motor genérico reutilizable por DiDi/Rappi y migración universal a eventos “canónicos”. Hacer Uber correctamente primero; extraer cuando exista un segundo proveedor.
- `DeliveryOutboundStream`, secuencias universales y un outbox compartido para órdenes, menú y pausa. Es correcto para una plataforma madura, pero mayor que el problema inicial.
- Persistir el token de aplicación en PostgreSQL. La documentación exige cache/reuso, no almacenamiento DB.
- OAuth self-service completo, selección multi-tienda y `UberOAuthSession`, si el piloto se provisiona por un flujo ops controlado. Sí será necesario antes de self-service.
- Publicación y auto-sync de menú, si el store piloto ya tiene menú y se confirma un mapeo estable `Uber item → Product.sku`. Si no existe ese mapeo, una publicación inicial o una tabla de mapeo se vuelve prerequisito de stock, no “nice to have”.
- Pedidos con efectivo, entrega propia, parciales, programados, cambios del cliente y sustituciones. Deben rechazarse visiblemente, no aceptarse a medias.
- Reembolso financiero y reposición automática tras cancelación posterior a la preparación. No se debe implementar hasta saber si Uber todavía paga al comercio y si el producto ya se consumió.
- Pausa automática por pérdida de plan, `PAUSE_PENDING`, dashboard completo de pausa y auto-sync. Para el piloto puede operarse desde Uber Manager, manteniendo el link local visible.
- Ticket EXPO, KDS especial y métricas MCP del outbox.
- Conciliación de depósitos y comisión real de Uber.
- Candado global a `Product.sku` y tabla de IDs externos versionados.
- Recibo del cliente: para producir el pedido basta la comanda de cocina. Si “se imprima” significa también recibo del comercio, agréguese como segundo `CloudPrintIntent`; EXPO sigue siendo opcional.

### 3.2 VERIFICADO EN LA DOCUMENTACIÓN DE UBER
- OAuth publica dos flujos: `client_credentials` para store/menu/order/report y `authorization_code` para activación. Los tokens muestran `expires_in=2592000`, duran 30 días y el límite documentado es 100 solicitudes de token por hora; Uber pide cachearlos y reutilizarlos. [Authentication](https://developer.uber.com/docs/eats/guides/authentication).
- Uber documenta una Primary Webhook URL por aplicación. `orders.notification` contiene IDs/resource URL; la orden completa se consulta después. El ACK esperado es 200 con body vacío. [Webhooks](https://developer.uber.com/docs/eats/guides/webhooks).
- La guía publicada documenta `X-Uber-Signature` como HMAC-SHA256 hexadecimal del body crudo usando el **client secret**. Esto contradice la Signing Key dedicada observada en el dashboard; no debe resolverse eligiendo una de las dos sin capturar un webhook firmado. [Webhooks, sección Security](https://developer.uber.com/docs/eats/guides/webhooks).
- La guía legacy exige accept/deny dentro de 11.5 minutos y describe hasta siete entregas del webhook. [Webhooks](https://developer.uber.com/docs/eats/guides/webhooks).
- La suite vigente “Order Fulfillment API 1.0.0” documenta:
  - `GET /v1/delivery/order/{order_id}`
  - `POST /v1/delivery/order/{order_id}/accept`
  - `POST /v1/delivery/order/{order_id}/deny`
  - `POST /v1/delivery/order/{order_id}/cancel`
  - `POST /v1/delivery/order/{order_id}/ready`
  También modela dinero con `amount_e5`, no con centavos. [Order Fulfillment API 1.0.0](https://developer.uber.com/docs/eats/references/api/order_suite).
- Las rutas legacy también siguen publicadas: `GET /v2/eats/order/{id}` y `accept_pos_order`. Por tanto no es válido mezclar ambas generaciones en un mismo adapter. [Legacy Get Order](https://developer.uber.com/docs/eats/references/api/v2/get-eats-order-orderid), [legacy Accept Order](https://developer.uber.com/docs/eats/references/api/v1/post-eats-order-orderid-acceptposorder).
- En el contrato legacy, `charges.total` es lo que el comercio espera recibir, excluyendo marketplace fees; `cash_amount_due` aplica a entrega por el comercio y puede diferir por créditos, promociones y cargos al cliente. No documenta por sí solo el split contable que la spec inventó. [Legacy Get Order](https://developer.uber.com/docs/eats/references/api/v2/get-eats-order-orderid).
- La suite de activación documenta `POST /v1/eats/stores/{store_id}/pos_data` con JSON body y `webhooks_config.webhooks_version: "1.0.0"`. La duda “query vs body” de la spec ya no aplica a esta suite. [Integration Activation API 1.0.0](https://developer.uber.com/docs/eats/references/api/integration_activation_suite).
- El endpoint legacy de status es exactamente `GET /v1/eats/store/{store_id}/status`, singular, con `{status, offlineReason}`. El POST legacy usa el mismo path, espera `ONLINE|PAUSED` y documenta 204. [Get Restaurant Status](https://developer.uber.com/docs/eats/references/api/v1/get-eats-stores-storeid-status), [Set Restaurant Status](https://developer.uber.com/docs/eats/references/api/v1/post-eats-stores-storeid-status).
- La suite Store 1.0.0 usa otras rutas y otro shape: `GET /v1/delivery/store/{id}/status` y `POST /v1/delivery/store/{id}/update-store-status`, con `ONLINE|OFFLINE` y campos snake_case. [Store API 1.0.0](https://developer.uber.com/docs/eats/references/api/store_suite).
- Menu v2 exige precios enteros en la fracción mínima de moneda; para MXN eso corresponde a centavos. `tax_info.vat_rate_percentage` significa impuesto incluido, pero la doc no fija una tasa mexicana concreta. [Put Menu](https://developer.uber.com/docs/eats/references/api/v2/put-eats-stores-storeid-menu).
- `MultiLanguageText.translations` es un mapa de locales. La documentación recomienda códigos con idioma y país, por ejemplo `en_us`; no establece que texto español deba publicarse bajo `en`. [Get Menu](https://developer.uber.com/docs/eats/references/api/v2/get-eats-stores-storeid-menu).
- La guía de sandbox afirma que la actividad está aislada de comerciantes de producción. Esa afirmación oficial contradice la prueba viva reportada. [Sandbox & Testing](https://developer.uber.com/docs/eats/guides/sandbox).
